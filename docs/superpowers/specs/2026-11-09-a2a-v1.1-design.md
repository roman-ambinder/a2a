# A2A v1.1 support

Date: 2026-11-09. Status: draft, for review.

## Goal

Make the SDK fully compliant with A2A **v1.1** (upstream tag `v1.1.0-rc`, commit `78e1d6a`), on JSON-RPC, HTTP+JSON and gRPC, for both client and server, while v1.0 (and the optional v0.3 layer) keep working unchanged.

## Where we are

- v1.0 is done. `docs/a2a.proto` equals upstream `main`. ACTS passes on all bindings. The only TCK failures are three TCK bugs and one allowed `MAY` choice (see `conformance/README.md`).
- No official SDK implements v1.1 yet (checked a2a-python, a2a-js, a2a-go, a2a-java, a2a-dotnet). There is no v1.1 TCK. We define behavior from the spec text, the proto and ADR-002.

## Decisions

### D1. Version negotiation and opt-in

- The server serves `1.0` and `1.1` side by side. The version comes from `A2A-Version` (gRPC: `a2a-version`) per call, as today.
- v1.1 is **opt-in while upstream is a release candidate**: `A2AServerOptions.EnableProtocolV11()` adds `"1.1"` to `SupportedVersions` and lists a `1.1` entry for each mapped binding in `supportedInterfaces`, before the `1.0` entries (the first entry is preferred, 8.2.1). New public types are `[Experimental("A2AEXP005")]`. New properties on existing types are not marked: the attribute on a property crashes the System.Text.Json 8 source generator used for netstandard2.0. The versioning guide says they follow the same rule. When 1.1 is final, the switch flips to on by default and the attribute goes.
- Every 1.1-only wire field and event is **hidden from 1.0 callers**: `generation`, `timeline`, `startGeneration`, `endGeneration`, `role`, `userArtifacts`, `protocolVersion` (push), and `messageUpdate`. Reason: strict ProtoJSON parsers reject unknown fields, and the spec already gates `messageUpdate` the same way. A 1.0 caller sees exactly what it sees today. This keeps the TCK and ACTS results unchanged.
- The client sends `A2A-Version: 1.1` only when the chosen interface declares `1.1` and `A2AClientOptions.PreferredProtocolVersion` allows it (default `1.0` while experimental, then `1.1`). No silent fallback when a caller asks for 1.1 features on a 1.0 agent: the call throws `NotSupportedException` before sending (3.6.3).

### D2. Generation equals the event sequence

The event log already gives each task event a sequence that starts at 1 and goes up by 1 per commit, and each commit stores exactly one event. So **generation = event sequence**, with one change: a follow-up message is now committed as an event (`messageUpdate`) through `TaskStore.CommitAsync`, not stored with `UpdateAsync`. Then:

- task created → snapshot event, sequence 1 → `generation = 1` (3.2.7);
- each status update, artifact update and client message → +1;
- replay from a generation is `EventStore.ReadAfterAsync(sequence)`, which already exists;
- nothing else (metadata stamps, pending-start markers, usage) changes the generation, because those writes use `UpdateAsync` and add no event.

Batched commits (`IBatchTaskCommit`, several artifact appends in one task write) keep one sequence per event, so the rule holds: a batch of n events raises the stored generation by n, and event i of the batch has generation `first + i`.

`AgentTask.Generation` is stored in the task. The engine sets `next.Generation = current.Generation + 1` before it commits. The store keeps the rule "event sequence == task generation" (checked by a new store conformance test in `A2A.Stores.Tests`). A conflict retry recomputes it on the fresh record, and the event is encoded again.

Stored event bytes are the 1.0 shape (`A2AJson.V10Options` hides every 1.1 member), so they stay valid for 1.0 callers and the 1.0 path writes them as they are. A 1.1 writer encodes the event again with the 1.1 members (`EventEncoder.JsonFor`); when the event model has no `generation` (it was rebuilt from stored bytes), it adds `"generation":"<n>"` from the sequence (one byte splice before the last two `}`). gRPC sets it on the proto the same way. Push deliveries do this by the config's version (PR 3).

**Tasks stored before the upgrade** have `Generation = 0`. On the first read or commit, the engine sets it from `EventStore.LastSequenceAsync` (the same value, because old follow-ups added no events). Old history entries have no timeline entry (see D3).

`messageUpdate` events are stored like other events, so replay and push see them, but they are never sent to 1.0 callers or 1.0 push configs. A 1.0 caller sees a gap in sequences only through `generation`, which it never sees.

### D3. Timeline

- Stored in `AgentTask.Timeline`, next to `History`. `History` stays the source for everything that reads it today (turn cap, duplicate message ids, memory, elicitation). Both are written in the same `ApplyToCopy` step:
  - status update → `TimelineEntry{ status, generation }`, plus the message into `History` as now;
  - client message (create or follow-up) → `TimelineEntry{ message, generation }`, plus `History` as now;
  - artifact add → `startGeneration` = generation; `lastChunk` → `endGeneration` = generation. An artifact replaced without `append` gets a new `startGeneration`.
- Cost: messages are stored twice. `MaxTaskBytes` counts both. Documented in the limits guide. A later version may derive `History` from `Timeline`; that is out of scope here.
- `timelineLength` follows the `historyLength` rule (unset = all, 0 = none, n = newest n), capped by a new `A2ALimits.MaxTimelineLengthReturned` (default 100).
- Tasks from before the upgrade: the timeline starts at the upgrade. It is not rebuilt from `History`, because the old generations are not known.
- Unknown `TimelineEntry` kinds from a peer are kept as entries with neither `message` nor `status` (`IsUnknownKind`), and readers skip them (F11). Their content is not kept.

### D4. Long-poll (GetTask `currentGeneration`)

- If the task's generation is greater than the value, or the value is unset: answer at once.
- Otherwise wait on the existing `TaskEventBus` for the next event of that task, then answer with a fresh read. Wait at most `A2AServerOptions.LongPollTimeout` (default 30 s, max 5 min), then answer with the current task (MAY return early).
- Each waiting call counts against the same open-stream budget per caller as SSE streams, so long-polls cannot exhaust the server. A terminal task answers at once (nothing changes it any more).
- 1.0 callers: the field is not in 1.0, so it is ignored (a strict check would refuse it; we are lenient on input, as for unknown fields today).

### D5. `ifGenerationMatch`

Checked under the task lock, on the record that the follow-up commit is based on, so the check and the commit are one step (CAS). Mismatch → `TaskGenerationMismatchError` with `ErrorInfo` reason `TASK_GENERATION_MISMATCH`, metadata `taskId`, `expectedGeneration`, `currentGeneration` (spec 11.6 example). Ignored for a new task. The idempotency replay check runs first: a retry of an accepted request returns the original result, not a mismatch.

### D6. Message event and streams staying open

- A follow-up commit emits `messageUpdate{ taskId, contextId, message, generation }`. Every other 1.1 stream of the task gets it. The sender's own stream starts after it, because the task it opens with already holds the message (as 3.1.12 says for a live `sendMessage`).
- **Streams of 1.1 callers stay open on `INPUT_REQUIRED` and `AUTH_REQUIRED`** (3.1.2 SHOULD NOT close): when no execution runs, the send stream continues as a subscription of the task. It closes on a terminal state, on client disconnect, or at `A2ALimits.MaxStreamDuration` (clients resume). No separate idle timeout was added: the existing stream limits already bound it. 1.0 streams keep today's rule.

### D7. Messages in any non-terminal state

4.1.3 now says the server MAY accept messages in any non-terminal state. The default stays `FollowUpPolicy.InterruptedOnly` for unary and streaming sends (MAY, and safer). Live streams use the agent's live input (D8). No new policy value is needed: `AllowSteering` already covers `Submitted` and `Working`.

### D8. Live streaming (`SendLiveMessage`)

**Agent side.** A running agent can take input while it works:

```csharp
public sealed class AgentRequestContext
{
    // null when the agent did not opt in
    public ILiveInput? LiveInput { get; init; }
}

public interface ILiveInput
{
    // Messages and client artifact updates that arrive while this execution runs, in order.
    IAsyncEnumerable<LiveInputItem> ReadAllAsync(CancellationToken cancellationToken);
}
```

- An agent opts in with `builder.AddAgentExecutor<T>(o => o.AcceptsLiveInput = true)`. Then a message that arrives while an execution of the task is running is committed (timeline + `messageUpdate`) and handed to that execution's `LiveInput`. No second execution starts.
- If no execution is running, the message starts one, as a follow-up does today (state rules of D7 apply).
- If the agent did not opt in and the task is `Working`, the request is refused with `StreamError{ code: "UNAVAILABLE" }` and the stream stays open (3.1.12: an agent MAY decline a single request).
- `LiveInput` has a bounded buffer (`A2AServerOptions.Streaming.LiveInputCapacity`, default 32). When full, the request is refused with `StreamError{ code: "RESOURCE_EXHAUSTED" }`; nothing is committed.

**gRPC.** Native bidi stream. The first `StreamRequest` binds the stream to one task (3.1.12):

- `sendMessage` first → handled like `SendStreamingMessage` (create or continue), the first frame is the `Task` snapshot that already contains the message;
- `subscribe` first → `lastSeenGeneration` set: replay events after it, no snapshot; unset, or no longer retained: snapshot, then live events;
- later requests: `sendMessage` for the bound task → commit, events come on the same stream; another task, a late `subscribe`, an unknown payload kind, a malformed request, missing capability → `StreamError` with `referenceId` (message id or artifact id), stream stays open.

**HTTP (JSON-RPC and REST).** The spec says the first call's response is the downlink and later input goes in short calls to the same operation, but not how the server tells them apart. **We use the `Accept` header:**

| Call | `Accept` | Server answers |
|---|---|---|
| Downlink | `text/event-stream` | SSE stream, same rules as gRPC above |
| Uplink | `application/a2a+json` (REST) or `application/json` (JSON-RPC) | One JSON response: the current `Task` (ack). No events (3.1.12 MUST NOT replay) |

- An uplink call must name its task (`message.taskId`, or `taskId` on each artifact update). `subscribe` on an uplink call is `InvalidParams`.
- An uplink call that is refused fails as a normal unary error **and** sends a `StreamError` on that task's live downlinks of the same owner, so a client that reads only the downlink also sees it. Clients built with this SDK read the unary error and drop the matching `StreamError` by `referenceId`.
- This choice is flagged as an open question upstream (see Risks); it only uses headers that every HTTP client already sets.

**Client API.**

```csharp
await using var live = await client.OpenLiveAsync(LiveStart.NewTask(message), ct);  // or LiveStart.Attach(taskId, lastSeenGeneration)
await live.SendAsync(Message.FromUser("more input"), ct);                         // gRPC: on the stream; HTTP: an uplink call
await live.SendArtifactAsync(update, ct);
await foreach (var evt in live.Events.WithCancellation(ct)) { ... }                 // includes StreamErrorEvent and MessageUpdateEvent
```

`OpenLiveAsync` throws `NotSupportedException` when the card has no 1.1 interface or `streaming` is off.

**As built (PR 5).** Differences from the plan above:

- No `AcceptsLiveInput` option: `AgentRequestContext.LiveInput` is always set, and the agent opts in by reading it (first `ReadAllAsync`). Until then the D7 follow-up rules apply, so a message to a `Working` task is refused with `FAILED_PRECONDITION`.
- The buffer size is `A2ALimits.LiveInputCapacity` (32). Full → `RateLimited` (`RESOURCE_EXHAUSTED`, retry after 1 s).
- Client: `OpenLiveAsync(Message)` or `OpenLiveAsync(StreamRequest)` (a `subscribe` first attaches); `A2ALiveConnection.SendAsync(Message)` / `SendAsync(StreamRequest)` (artifact updates go in a `StreamRequest`). Transports opt in with `ILiveTransport`; `OpenLiveAsync` throws `NotSupportedException` for one that does not.
- HTTP uplink refusals are not de-duplicated: `SendAsync` throws and `Events` also has the `StreamErrorEvent`.
- gRPC: a request that does not map to the model (for example a message without parts) is refused on its own, with its message id as `referenceId`.

### D9. Client-written artifacts

- `AgentCapabilities.UserArtifacts` (card) and `A2AServerOptions.UserArtifacts` (limits: max artifacts per request 16, same size limits as agent artifacts).
- Off on the card → `UnsupportedOperationError` (or `StreamError` on a live stream).
- Order (3.2.1): append `message` first, then each artifact update in list order; each is its own commit and event, so each gets its own generation. `generation` sent by the client is ignored. Stored with `role = ROLE_USER`.
- Artifact ids are one namespace per task. A client update for an id the agent wrote (`role = ROLE_AGENT`) is refused with `InvalidParams`, and the other way round the agent's `TaskUpdater` cannot overwrite a user artifact. The same seal and append rules apply as for agent artifacts.
- `message` absent and no `taskId` on the updates → `InvalidParams` ("message is required to create a task").
- The agent reads them from `AgentRequestContext.UserArtifacts` (sent with the starting message) and from `LiveInput` (sent later).
- If the agent answers with a direct `Message` (no task), nothing is stored, as for a message alone.
- Same media type and size checks as message parts. `Part` URLs are untrusted input; fetch them only with `SafeHttp`.

### D10. Push `protocolVersion`

- Default: the version of the request that created the config (`"1.0"` if unset), as the proto says.
- A `1.0` config gets today's bodies: no `generation`, no `messageUpdate` deliveries. A `1.1` config gets `generation` and `messageUpdate`.
- An unknown version → `InvalidParams` at registration.
- The `A2A-Version` header on each POST is the config's version.

### D11. Small items

- REST subscribe: the client switches its default to `GET` for 1.1 interfaces (spec now agrees with the proto). The server already accepts both.
- Agent Card: serve `application/a2a-agent-card+json` when the request `Accept`s it, else `application/json` as today. The client sends `Accept: application/a2a-agent-card+json, application/json`.
- gRPC interface URL: the card generator already writes `host:port` (the conformance agent does); make it the default for `MapA2AGrpc`.
- `docs/a2a.proto` moves to the v1.1-rc proto. All changes are additive, so 1.0 gRPC peers are not affected (proto3 skips unknown fields). The generated code in `A2A.Grpc` and the mappers are updated.

## Testing

- Unit tests per feature, on all three bindings, for 1.0 and 1.1 callers. Every 1.1 test has a 1.0 twin that checks the wire is byte-identical to today.
- Store conformance (`A2A.Stores.Tests`): "sequence == generation" for in-memory and Postgres, upgrade backfill of tasks with generation 0.
- Concurrency: two clients with `ifGenerationMatch` on one task, exactly one wins. Long-poll wakes on each event kind and times out.
- Live: gRPC bidi and HTTP downlink+uplink; every `StreamError` case in D8; no event delivered twice to a client with downlink and uplink open.
- Interop: the existing Python interop must still pass (1.0). No external 1.1 suite exists; add our own 1.1 scenarios to `conformance/` as a local suite, to be replaced by the TCK's when it ships.
- `conformance/run.sh` (TCK + ACTS, 1.0) must show the same results as today.

## Delivery

One design, five PRs, each green on its own:

1. **Model and proto**: new models and fields, version-aware writer, proto v1.1-rc, gRPC regen, client parsing (F11, F12). No behavior change for 1.0.
2. **Generation, timeline, message event** (F1, F4, F5, F10, D2, D3, D6), store tests, Postgres migration.
3. **Long-poll, `ifGenerationMatch`, resume, push version** (F2, F3, F6, F9).
4. **Client-written artifacts** (F8).
5. **Live streaming** (F7) on gRPC, then HTTP; client `OpenLiveAsync`; docs (spec decisions, streaming guide, a new "v1.1" guide), CHANGELOG, README.

## Risks and open questions

- **The rc may change before 1.1 final.** Mitigated by opt-in and `[Experimental]`. Re-diff the proto on each upstream tag.
- **HTTP uplink/downlink split (D8)** is our reading; the spec does not define it. Raise it upstream (A2A repo issue) with this proposal so other SDKs match.
- **Uplink error reported twice (D8).** Chosen so downlink-only clients see it. Upstream may pick one channel.
- **Storage growth** from storing messages in `History` and `Timeline`. Accepted for v1.x; see D3.
- **Canonicalization (8.3.1)** is unchanged by 1.1. The signed payload stays the v1.0 schema, because that is what a2a-python and a2a-js verify today: adding `userArtifacts` to it would make every signed 1.1 card fail their checks. So `userArtifacts` on a signed card is not signed, and a verified card (built from signed content only) does not show it. Revisit when an official SDK signs the 1.1 schema; until then PR 4 documents that a client of a signed card must opt in to user artifacts by configuration.
