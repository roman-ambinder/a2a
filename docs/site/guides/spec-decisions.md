# Spec decisions

The A2A spec is loose or self-contradictory in places. This page lists what this SDK does in those places, and where it is stricter than the spec's SHOULDs. Read it when a peer built on another SDK behaves differently, or when you need to know which rule the SDK applies. Where a topic has its own guide, the decision is stated here in a line or two and the guide has the details. Section numbers in parentheses are the spec's.

## Security

These choices are stricter than the spec asks.

- **Task ownership** (spec 13.1). Each task is bound to the caller id and the tenant. The default <xref:A2A.Server.IPrincipalResolver> reads the `NameIdentifier` claim, then `sub`. Other callers get `TaskNotFound` and never learn that the task exists. `ListTasks` filters by owner and tenant before it counts or pages. Anonymous callers share one owner, so put `RequireAuthorization()` on the endpoints in production. See [Authentication and ownership](auth-and-ownership.md).
- **Per-caller limits for anonymous callers.** The rate limit and the open-stream budget count each anonymous caller by remote IP address (`anon:{ip}`). An IPv6 caller is counted by its /64 prefix (`anon:2001:db8:1:2::/64`), so one host cannot get a fresh budget per address. Behind a reverse proxy, call `app.UseForwardedHeaders()` before `UseA2A()`, with the proxy in `KnownProxies` or `KnownNetworks`. Without it, all anonymous callers share the proxy's budget. See [Limits and rate limiting](limits-and-rate-limiting.md).
- **Push SSRF guard.** A webhook URL must use HTTPS. Loopback, private, link-local (including the cloud metadata range 169.254/16), CGNAT and unique-local targets are rejected. They are rejected at registration and again at connect time, against the resolved IP, which blocks DNS rebinding. Through a configured `Proxy`, the connect-time check sees only the proxy, so the proxy must block internal addresses itself. Redirects are off. `PushNotificationOptions` can relax the scheme and network rules. See [Push notifications](push-notifications.md).
- **Card verification** (<xref:A2A.Signing.CardTrustPolicy>). A signature counts only if its key is pinned for the card's origin (`TrustedKeys`) or is served from a `jku` host that is allowlisted for that same origin. A key the card points at by itself is never trusted, so a forged card is `Unverified`, never `Verified`. The header `typ` must be `JOSE` or `JOSE+JSON`. The algorithm allowlist is ES256/384/512, RS256/384/512 and PS256/384/512; `none` and HS* are never accepted. An unknown `crit` is rejected, and the key type must match `alg`. A `Failed` status always stops resolution. Once trust is configured, `Unsigned` and `Unverified` cards are rejected unless `RequireSignature` is `false`. See [Agent Card signing](agent-card-signing.md).
- **Card pinning and untrusted text.** The resolver pins the SHA-256 of each origin's canonical card. A change raises `CardChanged`, logs a warning and counts `a2a.card.changed`. `PinPolicy.Strict` fails the resolution instead. Key rotation with the same content is not a change. `ResolvedAgentCard` exposes the description and skill text as `UntrustedText`: control and bidi characters are removed and the text is capped at 2000 characters. The card `name` is display only. An unsigned card that is accepted counts `a2a.card.unsigned`; see [Observability](observability.md#metrics).
- **Peer identity and agent registry.** A peer is a `PeerIdentity` (origin, key id, assurance), never its card `name`. `AgentRegistry` is keyed by identity: a duplicate name is rejected, and lookalike names are registered with a warning and counted. See [Peer identity and registry](peer-identity.md).
- **Executor errors.** An exception from your agent moves the task to `Failed` with the generic status text "The agent failed to process the request." The exception is logged, not sent. For other unexpected errors, <xref:A2A.Server.A2AServerOptions.IncludeExceptionDetails> controls whether the exception type and message are added to the error text. It is on only in Development by default.
- **No redirects on A2A calls.** A response that came through a redirect is refused (`InvalidAgentResponse`). An `HttpClient` that follows redirects would send custom credential headers to the new host (a2a-java CVE-2026-111763). Use `AddA2AClient`, which turns redirects off, or give your own `HttpClient` a handler with `AllowAutoRedirect = false`.
- **Delegation identity** (after [A2A#2028](https://github.com/a2aproject/A2A/issues/2028), which is still open). The `actorChain` in message metadata is audit, not authorization, and the hop limit (<xref:A2A.Server.A2ALimits.MaxActorChainHops>, default 8) is a loop brake, not a security boundary. Agent code never gets the caller's token; it exchanges it with an <xref:A2A.Delegation.ITokenExchanger>. Register one only when a Bearer handler validates the header. See [Authentication and ownership](auth-and-ownership.md#delegation).
- **Fetching `UrlPart` URLs** (spec 14.1.1). Use <xref:A2A.Security.Http.SafeHttp> from the `A2A.Security.Http` package (`CreateClient`, `DownloadAsync`). It applies the push SSRF rules (HTTPS only, private ranges blocked by resolved IP, no redirects) and a size cap.
- **Message and artifact content** (14.1.1). The SDK sanitizes the text it writes itself: logs, audit records and security events go through <xref:A2A.Text.TextSanitizer>, and card text is exposed as <xref:A2A.Client.Cards.UntrustedText>, with `ToHtml()` and `ToMarkdown()` for display. It does not change message parts or artifacts. They are stored and returned as JSON exactly as they were sent, because only the agent knows where they go next (a model prompt, a web page, a shell command, a database query) and so which escaping is right. Treat them as untrusted input in your agent: escape them for the place you write them to, never run them as instructions or code, and use `TextSanitizer.Sanitize` where stripping control, bidi and invisible characters helps. The [Extensions.AI](extensions-ai.md#untrusted-text) and [MCP](mcp-bridge.md#remote-text-is-untrusted) bridges also tell the model that remote text is untrusted data.
- **Task time limit.** <xref:A2A.Server.A2AServerOptions.MaxTaskDuration> is off by default. One agent run that goes over it moves the task to `FAILED` with "Task exceeded its time limit", and its cancellation token fires. A task that waits in `INPUT_REQUIRED` or `AUTH_REQUIRED` with no agent running is not affected. See [Task safety](task-safety.md).
- **Turn cap.** <xref:A2A.Server.A2AServerOptions.MaxTurnsPerTask> is off by default. It is a defense against multi-turn "agent session smuggling" (Unit 42). A follow-up that would go over the cap is refused with `UnsupportedOperation` before the agent runs. A custom `TaskStore` must keep the full history, because turns are counted from it. A retry with the same idempotency key is not a new turn. See [Task safety](task-safety.md).
- **Agent Card endpoint policy** (after [a2a-python#895](https://github.com/a2aproject/a2a-python/issues/895)). A card chooses the URL the client then calls, so a card from the internet could aim the client at an internal address (SSRF). <xref:A2A.Client.A2AClientOptions.EndpointPolicy> judges every interface the client could select, before it builds a client, on every factory path that fetches a card. The default on .NET 10 is <xref:A2A.Client.AgentEndpointPolicies.MatchCardNetwork>: a card from a private address (or one the caller supplied) may name private endpoints, a card from a public address may not. A refusal is `InvalidAgentResponse` that names only the host, and counts `a2a.client.endpoint.refused`. On netstandard2.0 there is no default policy, the same limit as the `jku` fetch. The check is pre-flight; see [Task safety](task-safety.md).
- **Security events** (spec 13.4 SHOULD). The server counts `a2a.server.security.events` with the tag `a2a.security.event` (`unauthenticated`, `permission_denied`, `context_denied`, `webhook_refused`, `idempotency_key_mismatch`) and writes one log line per event (ids 1200 and 1201) with a hash of the principal, never the principal. A caller who reads another caller's task cannot be detected, because the store lookup is scoped by owner and reads as `TaskNotFound`; the SDK does not add a lookup to find out. See [Observability](observability.md).
- **Anomaly monitoring** (spec 13.4 SHOULD: "monitoring for unusual patterns (rapid task creation, excessive cancellations)"). Opt in with <xref:A2A.Server.A2AServerOptions.Anomalies> (`Enabled`, default false). The server counts, per caller (principal and tenant) in a one-minute window, the SendMessage and SendStreamingMessage calls that create a task (not follow-ups or idempotent retries) and every authorized CancelTask call, whether or not the cancel succeeds. Over `TaskCreationsPerMinute` (default 60) or `CancellationsPerMinute` (default 20), it writes one `anomaly` security event per caller and window (log 1202) and counts `a2a.server.anomalies`. It only reports: no call is refused or delayed (that is the rate limiter's job). See [Observability](observability.md#anomaly-detection).
- **Deletion of a caller's data** (spec 13.4 SHOULD: "provide mechanisms for users to request deletion of their data"). A2A 1.0 defines no delete operation, so the SDK adds one as an opt-in SDK extension operation, not a core A2A method: `AddTaskDeletion()` serves `a2a.tasks.delete` (extension `https://github.com/roman-ambinder/a2a/extensions/task-deletion/v1`, listed on the card) and the client calls it with `DeleteTaskAsync(taskId)`. Owner only: another caller's task, or a missing one, is `TaskNotFound`, and anonymous callers are refused. Terminal tasks only: a task that is not terminal is `UnsupportedOperation` and is not cancelled for the caller, who can call `CancelTask` first. It deletes what the operator delete (`A2ATaskAdmin`) deletes and is audited as `TaskDeleted`. Without the call, nothing changes. See [Retention](retention.md#let-callers-delete-their-own-tasks).
- **Shared contexts.** A context belongs to the principal that created it, and another principal gets `InvalidParams` "contextId not found". <xref:A2A.Server.A2AServerOptions.ContextAccess> lets other principals join an existing context. Tasks stay owner-scoped: the second principal gets a task of its own and never sees the owner's tasks. The agent sees one `contextId` for both, so per-context agent memory is shared.
- **Client per-message hook.** <xref:A2A.Client.A2AClientOptions.OnMessageReceived> runs for every agent message `A2AClient` receives, on all bindings, unary and streamed. Throw to abort the call. Keep the check idempotent, because the same snapshot message can arrive more than once. See [Task safety](task-safety.md).

## Signing and forward compatibility

- **Canonicalization** matches a2a-python 1.2.1 and a2a-js 1.3.0. The card is reduced to the A2A v1.0 Agent Card schema, empty values are pruned, then RFC 8785 (JCS) is applied. **Fields outside the v1.0 schema (newer versions, extensions, v0.3 compatibility fields) and pruned values are not covered by the signature.** The resolver builds a verified card only from the signed content, so unsigned fields never reach it. The rule, the differences and the test vectors are in the [vectors README](https://github.com/roman-ambinder/a2a/blob/main/tests/A2A.Tests/Vectors/README.md). See also [Agent Card signing](agent-card-signing.md) and [Interop and conformance](interop-and-conformance.md).

## Protocol choices

- **Agent Card caching** (8.6). The public card has `Cache-Control: public, max-age`, an `ETag` and a `Last-Modified`. `Last-Modified` is when this process first served that content, so it differs between instances; the server does not answer `If-Modified-Since` with 304, and the entity tag alone decides, so a stale card is never confirmed. The client cache (<xref:A2A.Client.A2ACardResolver>) follows RFC 9111 as a private cache: `no-store` is not kept, `no-cache`, `Vary: *` and (without Cache-Control) `Pragma: no-cache` are revalidated on every use, and a card is fresh for `max-age` (else `Expires` minus `Date`, else `DefaultCacheDuration`) less its age (`Age`, or the time since `Date`). `s-maxage` is for shared caches and is ignored. It revalidates with `If-None-Match`, or `If-Modified-Since` when the server sent no entity tag.
- **Extended Agent Card caching** (13.3). Over HTTP+JSON, `GET /extendedAgentCard` answers with `Cache-Control: private, no-cache`, `Vary: Authorization, Cookie, A2A-Version` and an `ETag` of the bytes served. A client may keep the card but asks again before using it; an `If-None-Match` that still matches gets 304. The request is authorized and the card is built before the tag is compared, so a 304 tells a caller nothing it could not read. JSON-RPC (POST) and gRPC have no HTTP caching.
- **Patch versions** (3.6). The client sends `A2A-Version` as Major.Minor: a card interface or `A2AClientOptions.ProtocolVersion` of `1.0.2` is sent as `1.0` (<xref:A2A.A2AProtocol.ToMajorMinor*>).
- **Client version selection** (3.6.2, 3.6.3, 8.3.2). <xref:A2A.Client.A2AClientOptions.ProtocolVersion> is the newest version the client speaks. `A2AClientFactory` selects, in the card's order, the first interface of the same major version and no newer minor, and sends that interface's version. So a 1.0 client skips a 1.1 interface that the card lists first (this SDK's server does, once `EnableProtocolV11()` is called) and calls the 1.0 one with `1.0`, and an interface of a newer minor version (`1.7` to a 1.0 client) is never selected. A 1.1 client uses a 1.0 interface with `1.0` when the card prefers it. <xref:A2A.Client.A2AClientOptions.RequireExactProtocolVersion> keeps a client to its own minor version, with no fallback to an older one.
- **Card interfaces at startup** (5.2, 8.3.1, 13.4). Once the app has started, the server checks the host's Agent Card and warns (it never stops the app): a mapped binding the card does not list (event 703), a binding mapped at a tenant pattern such as `/{tenant}/a2a`, which is never listed automatically (704; list it in each tenant's card), and, outside Development, an interface on a local address (702; set <xref:A2A.Server.AspNetCore.A2AHttpOptions.PublicBaseUrl>), an interface on plain HTTP (705), and a server with no HTTPS listen address and no https `PublicBaseUrl` (706; ignore it when a proxy in front terminates TLS, and set `PublicBaseUrl` to the proxy's https address). The default `{pattern}/{tenant}` routes of `MapA2A` are not reported.
- **Interface fallback** (5.2: clients SHOULD fall back to alternative protocols). Opt-in with <xref:A2A.Client.A2AClientOptions.InterfaceFallback>, off by default. The client moves to the next acceptable interface of the card (same tenant, card order) only when a call failed before any request reached the agent: a connection, name lookup, proxy tunnel or TLS handshake failure, after the transport's retries, and for a stream only before its first event. An HTTP status, an A2A error, a timeout or a failure during the request never falls back, because the agent may have acted on it (a REST 404 is `TaskNotFound`). The interface that worked is kept for later calls. With credentials, only interfaces the credentials may go to are candidates. See [Client resilience](client-resilience.md#interface-fallback).
- **JSON model and the proto** (1.4). The JSON model is written by hand, not generated. `tests/A2A.Grpc.Tests/ProtoModelDriftTests.cs` compares it with the types generated from `docs/a2a.proto` on every build: each message, field, union case and enum value of the proto must be in the model.
- **Card authentication schemes** (7.4, 13.3). The SDK does not check by itself which scheme authenticated a caller, because your ASP.NET Core schemes have their own names. <xref:A2A.Server.AspNetCore.A2ACardAuthenticationExtensions.RequireAgentCardSchemes*> maps card schemes to them and requires one of the card's security requirements. Opt in; see [Authentication and ownership](auth-and-ownership.md#use-the-schemes-the-card-declares).
- **Webhook hygiene on the client** (13.2). <xref:A2A.Client.A2AClientOptions.RequireHttpsWebhooks> refuses plain-HTTP webhook URLs (loopback allowed); it is off by default because test receivers, including the TestKit's, use plain HTTP. `RegisterPushAsync` gives a config without credentials its own random token, <xref:A2A.Client.A2AClient.RotatePushTokenAsync*> replaces a token without a gap, and <xref:A2A.Client.Push.PushNotificationReceiver.MaxDeliveriesPerMinute> limits accepted deliveries (opt-in). See [Push notifications](push-notifications.md#register-a-webhook-safely).
- **Push task ids** (4.3.3). <xref:A2A.Client.Push.PushNotificationReceiver> checks that a notification is for an expected task only when you set `ExpectedTask`, because only your app knows which tasks it created. See [Push notifications](push-notifications.md#receiving-deliveries).
- **`jku` key sets** (8.4.3). A fetched key set is kept for the lifetime its response gives, at most 10 minutes, so a removed key stops verifying when that lifetime ends. A fetcher that only implements `IJwksFetcher` keeps the 10-minute cache.
- **JSON-RPC envelope** (9.3). A request without `"jsonrpc": "2.0"` is `InvalidRequest` (`-32600`), also when the member is missing, on the v1.0 endpoint and on the v0.3 surface. A member of the wrong JSON type stays a parse error (`-32700`), as before.
- **Missing `A2A-Version`.** The spec says a missing header means 0.3 (3.6.2), and the server rejects that. Set <xref:A2A.Server.A2AServerOptions.TreatMissingVersionAsCurrent> to `true` to accept curl-style calls. That breaks the MUST ("Agents MUST interpret empty value as 0.3 version"), so outside Development the server logs a warning at startup (event 709); `UseDevelopmentDefaults()` and the templates turn it on in Development only.
- **Cards older than 1.0.** `A2AClientFactory` and a plain `A2ACardResolver` never read a v0.2 or v0.3 card (a card without `supportedInterfaces` whose `protocolVersion` is `0.x`, or that has a top-level `url` and no `protocolVersion`) as a 1.0 card: they refuse it with `InvalidAgentResponse` and an error that names `V03CompatClientFactory`.
- **v0.3 compatibility.** The v0.3 surface is optional and separate. The SDK has no deprecated alias types for v0.3 names (1.4 asks SDKs for them): v0.3 JSON is read and written by the separate compat packages, which map it to the v1.0 model, so v1.0 code never sees the old names. The OAuth flows the spec deprecated (implicit, password) stay in the model and are marked `[Obsolete]`. A call without `A2A-Version` is still refused on the v1.0 methods (unless `TreatMissingVersionAsCurrent` is on). The v0.3 surface serves an absent version and `0.3`/`0.3.x` only; any other version is `VersionNotSupported` (3.6.2). v0.2.x peers use it over JSON-RPC: the card is also served at `/.well-known/agent.json`, and the compat client reads v0.2.x cards. v0.3 push configs are served; their webhook body is the task as a v0.3 `Task`, what the v0.3 Python SDK sends. See [v0.3 compatibility](v03-compatibility.md).
- **Required-field validation.** The client refuses a request that lacks a field the proto marks REQUIRED, before it sends anything, with `InvalidParams`. This holds on every `A2AClient` binding. The fields are the message, its `role`, `parts` and each part's content; the task id (`id` or `taskId`) and push config `id`; push config `url`, and `authentication.scheme` when authentication is set (also `taskId` on a push config you create). `A2AClient` fills in a blank `messageId` instead of refusing it. It checks presence only. It does not apply the server's URL and signing-secret rules. A transport you build by hand (for example `new JsonRpcTransport(...)`) is not validated. The server has its own, stricter inbound checks, for every operation, on every binding.
- **Proto field names.** Requests may use proto names (`history_length`) as well as JSON names (`historyLength`), in JSON bodies and in REST query strings (the ProtoJSON parser rule, A2A #2087). Keys inside `metadata`, data parts, extension `params` and maps keep their spelling. Both spellings of one field in one object is `InvalidParams`.
- **Stream errors.** An error after a REST stream has started is sent as an SSE frame named `error` with a `google.rpc.Status` body (A2A #1262, which is what a2a-python reads). JSON-RPC stream errors stay unnamed JSON-RPC error responses. The client accepts both. It skips stream events of a type it does not know (a newer protocol version) instead of ending the stream (A2A #2269).
- **Extensions.** Required extensions are enforced. The server echoes the activated extensions in the `A2A-Extensions` response header, so clients can tell what was honored. The echo is the header (or gRPC metadata), on unary and streaming calls, sent before the first event. There is no copy in the event body, because A2A#2428 is unsettled and no SDK does that.
- **Skill selection.** An optional extension from A2A epic #1989: the client names a skill in `metadata["skillId"]`, and an agent can refuse a skill it does not have. The id is a hint, not authorization. Plain v1.0 peers ignore it. See [Skill selection](skill-selection.md).
- **Skill authorization.** A2A v1.0 has no field for the skill a message wants, and upstream epic #1989 is open, so the SDK reads the same `metadata["skillId"]` key as skill selection and checks it with `A2AAuthorizationHandler.AuthorizeSkillAsync`. When a mode is on, the key counts without the `A2A-Extensions` header or a card entry, because a security check must not depend on a header. The key may move if the upstream epic lands. See [Skill authorization](skill-authorization.md).
- **Structured elicitation.** An optional extension for forms in `INPUT_REQUIRED`, in `Elicitation.ExtensionUri`. An agent declares it with `Elicitation.CreateExtension()` and asks with `TaskUpdater.RequireInputAsync(context, form, text)`. A client activates it with `UseElicitation`, reads the form with `GetElicitationForm()` and answers with `AnswerElicitationAsync`. The form and the answer travel in message metadata, and the text part always says what is needed, so a plain peer can answer in words. The agent decides what accept, decline and cancel mean. A refused answer is `InvalidParams`, is not stored and uses no turn. Fields that look like secrets are refused by default. See [Task safety](task-safety.md).
- **REST subscribe.** The spec text says `POST /tasks/{id}:subscribe`, but the normative proto says `GET`. The server accepts both. The client uses POST by default (<xref:A2A.Client.A2AClientOptions.RestSubscribeMethod> changes it). A POST carries the A2A 1.1 `lastSeenGeneration` in its JSON body, a GET in the query string; on a POST the body wins over the query.
- **Blocking and non-blocking SendMessage** (3.1.1, 3.2.2). The two sections disagree: 3.1.1 says SendMessage "MUST return immediately", while 3.2.2 says a send without `returnImmediately` is blocking, the default, and "MUST wait until the task reaches a terminal state … or an interrupted state". The SDK follows 3.2.2. SendMessage blocks unless `returnImmediately` is true. With `returnImmediately: true` it returns as soon as the agent's first event has created the task, or with the `Message` when the agent replies directly. A blocking call returns when the task becomes terminal or interrupted, whether by an event of this execution or of another one (for example `CancelTask`). It also returns when this execution has ended and no execution of the task is running on any instance, because nothing left could change the task. So an agent that returns while leaving its task in `WORKING` (for example to continue it later on its own) answers its blocking caller with a `WORKING` task, which 3.2.2 does not foresee. The caller then polls with GetTask, subscribes, or, with this SDK's client, sets <xref:A2A.Client.A2AClientOptions.WaitForTaskCompletion>.
- **Stream closing.** A send stream ends on a terminal state, including one set by another execution such as `CancelTask`, or when the executor returns and no other execution of the task is running. `AUTH_REQUIRED` keeps the stream open while the executor waits for out-of-band credentials (7.6.1). `SubscribeToTask` ends on a terminal state. See [Streaming](streaming.md).
- **Push delivery.** The deliveries of an event (one per push config) are written to a durable outbox in the same atomic commit as the event. A hosted `PushDeliveryService` sends them at least once, in order per task and push config, with exponential backoff and jitter. Defaults (<xref:A2A.Server.A2AServerOptions.PushDelivery>): 1 s initial wait, 5 min maximum, no limit on the number of attempts (`MaxAttempts` null), and a delivery still failing 24 hours after it was queued is dead-lettered (`MaxDeliveryAge`). A refused URL, any status other than 2xx, 408, 429 or 5xx, a delivery over `MaxDeliveryAge`, or a failed last attempt when `MaxAttempts` is set moves the delivery to the dead letters, which <xref:A2A.Server.Push.A2APushAdmin> lists and re-drives. Each POST carries `A2A-Version`, `X-A2A-Notification-Token` (when the config has a token), an `X-A2A-Delivery-Id` that stays the same across retries, and `X-A2A-Notification-Sequence`. The sequence is an SDK extension: a per-task counter for deduplication and ordering, which the spec does not define. The counters are `a2a.server.push.deliveries` and `a2a.server.push.dead_letters` on the `A2A.Server` meter; see [Observability](observability.md#metrics). See [Push notifications](push-notifications.md) for retry rules, the outbox and re-drive.
- **Webhook signatures** ([Standard Webhooks](https://www.standardwebhooks.com/)). Register the push config with `authentication.scheme = "webhook-signature"` and `credentials = "whsec_" + base64(secret)` (at least 16 bytes). Every POST then carries `webhook-id`, `webhook-timestamp` and `webhook-signature`, and the secret is never sent as an `Authorization` header. The receiver checks it with <xref:A2A.Client.Push.PushNotificationReceiver.VerifySignature*>. The result is `Valid`, `InvalidSignature`, `Stale` (the timestamp is outside the tolerance, 5 minutes by default) or `Duplicate`. Pass the raw body bytes, not re-serialized JSON. See [Push notifications](push-notifications.md).
- **Error details** (spec v1.0.1 §3.3.2, §9.5, §11.6). Every error carries a `google.rpc.ErrorInfo` first, on all bindings. An invalid request field (a missing `messageId`, a push config URL that is not absolute http(s), and the other checks of `A2AValidator`) also carries a `google.rpc.BadRequest` with the field and the reason; <xref:A2A.A2AException.InvalidField*> builds such an error. Each detail object must have an `@type`, so an entry of <xref:A2A.A2AException.Details> that is not an object with a non-empty `@type` is left out of the response. Over gRPC, `ErrorInfo`, `RetryInfo` and `BadRequest` are sent; other detail types are HTTP only.
- **Auth errors.** The HTTP layer answers 401 or 403 with `WWW-Authenticate`. Over JSON-RPC the body uses code `-32603` with an `ErrorInfo` reason of `UNAUTHENTICATED` or `PERMISSION_DENIED`, because the spec assigns no JSON-RPC number to them. Over gRPC, an `UNAUTHENTICATED` status carries a `www-authenticate` metadata entry with the same scheme as the HTTP header: the first HTTP auth scheme of the card of the call's tenant, else `Bearer`.
- **Push config delete.** `DeleteTaskPushNotificationConfig` is idempotent (3.1.10): deleting a config that does not exist succeeds. An unknown task is still `TaskNotFound`.
- **Media types.** A message part with a `mediaType` that the card does not accept (default input modes plus every skill's input modes; `type/*` and `*/*` match, parameters are ignored) is refused with `ContentTypeNotSupported` (-32005) before anything is stored. A card that declares no input modes accepts everything. Parts without a `mediaType` are never checked.
- **Artifacts.** `append: true` adds the parts to the stored artifact with the same id, or creates it when there is none. Without `append`, the artifact is created or replaced, also after `lastChunk`. `lastChunk: true` seals the artifact: an append to a sealed artifact is rejected. Empty `parts` are allowed only for an append to an artifact that exists. The server stores the seal as `a2a.artifact.sealed` in the artifact's metadata. See [Artifact chunks](streaming.md#artifact-chunks).
- **Required card arrays** (5.7). The proto makes `supportedInterfaces`, `defaultInputModes`, `defaultOutputModes`, `skills` and `AgentSkill.tags` REQUIRED, so each must have at least one element. The SDK reads cards leniently: a missing or empty array is read as empty, so a client still accepts another agent's card that leaves one out. The server refuses to serve a card with no `supportedInterfaces` and none it can fill in from the mapped bindings. For the others it logs a warning at startup (event 708) and serves the card as it is.
- **Required fields in responses** (5.7). The client rejects an agent response that lacks a REQUIRED field with `InvalidAgentResponse`: a task without an `id` or a status `state`, a status, artifact or message update without its `taskId` or `contextId`, a message without a `messageId`, a `role` or parts, and an artifact without an `artifactId` or parts (an append chunk and a stored artifact may have no parts). This covers SendMessage, GetTask, ListTasks, CancelTask and every stream event. <xref:A2A.Client.A2AClientOptions.ValidateResponses> = false turns it off for a peer that leaves fields out. A fetched Agent Card is still read leniently: the resolver logs a warning (event 103) once per origin that lists the REQUIRED card fields it lacks, and uses the card.
- **Event metadata** ([A2A#1374](https://github.com/a2aproject/A2A/issues/1374), still open). The `metadata` of a status update event and of an artifact update event merges into `Task.metadata`: shallow, last write wins. A key that is not in the update stays. A key cannot be removed, and JSON `null` is stored as a value. An agent cannot write the server-owned keys `a2a.approval.consumed`, `a2a.cancelRequested`, `a2a.elicitation.answered`, `a2a.followUp.pendingStart`, `a2a.usage` and `actorChain` this way. See [Metadata keys](metadata.md). `Artifact.metadata` merges into the stored artifact on `append: true` and replaces it otherwise. #1374 proposes that artifact event metadata is transient; this SDK merges it, so both event types follow one rule.
- **Large artifacts.** The spec has no way to fetch part of an artifact, so a large file is a normal `url` part. With an `ArtifactObjectStore` registered, the server uploads a raw part over `ArtifactStorage.InlineThresholdBytes` (256 KiB), or a stream from `TaskUpdater.AddArtifactFromStreamAsync`, and writes a part whose URL is `{base}/artifacts/{tenant}/{taskId}/{objectId}`. The part metadata holds `sha256` (the object's bytes) and `sizeBytes`. Downloads use the caller's A2A credentials and are authorized as `GetTask`: there are no signed links that work without credentials, so a client of another SDK must send them. Appended chunks stay inline. `MaxTaskBytes` (64 MiB) and `MaxArtifactsPerTask` (1024) cap every task, with or without a store. See [Artifact storage](artifact-storage.md).
- **Raw events.** A2A v1.0 has no method to read a task's events. On the server, use `ReadAfterAsync` on the <xref:A2A.Server.Storage.EventStore> from DI. It is scoped to the owner in the `TaskKey`. It returns only the retained events: the last `ReplayBufferSize` per task, until retention removes them.
- **History timestamps** (A2A epic #1991). The server adds `metadata["a2a.message.recordedAt"]` (UTC, ISO 8601) to each message it adds to the history, and overwrites a value the client sent. For an agent message it equals `status.timestamp`. Read it with `Message.GetRecordedAt()`, which returns null for a message stored before this feature. The JSON and proto shape does not change, and the Postgres schema does not change. The time is informational: order messages by their position in the history.
- **`historyLength`.** One rule on SendMessage, SendStreamingMessage, GetTask and ListTasks: unset means all, 0 means none, n means the newest n. <xref:A2A.Server.A2ALimits.MaxHistoryLengthReturned> caps all of them. SubscribeToTask and a stream reconnect have no `historyLength` in v1.0, so they use the cap only. v1.0 has no history paging. A2A 1.1 callers also get the timeline (`timelineLength`).
- **Repeat CancelTask** ([A2A#2358](https://github.com/a2aproject/A2A/issues/2358), still open). The spec does not say what a second CancelTask of a canceled task should answer. The server default is `TaskNotCancelable` (-32002), because the TCK test `CORE-CANCEL-002` requires it. Set <xref:A2A.Server.A2AServerOptions.IdempotentCancel> to answer the canceled task instead. Other final states always give `TaskNotCancelable`. `A2AClient.CancelTaskAsync` is lenient on its own: on `TaskNotCancelable` it calls GetTask, returns the task if it is `CANCELED`, and otherwise throws the original error.
- **A2A 1.1 (release candidate).** The model and the proto follow `v1.1.0-rc` (experimental, `A2AEXP005`). 64-bit values (`generation`) are written as strings, as ProtoJSON does, and read as strings or numbers. A `TimelineEntry` or `StreamRequest` of a kind this SDK does not know is kept with `IsUnknownKind` set, so readers can skip it (1.1 §3.2.3, §3.2.8). The server serves 1.1 when `A2AServerOptions.EnableProtocolV11()` is called; see the next item. See the [design](https://github.com/roman-ambinder/a2a/blob/main/docs/superpowers/specs/2026-11-09-a2a-v1.1-design.md).
- **A2A 1.1 on the server.** One server serves 1.0 and 1.1; the `A2A-Version` header of each call decides. The task generation equals the task's event sequence: every stored event is one change, and a follow-up message is stored as an event too (a message update). Stored event bytes are the 1.0 shape, so 1.0 streams and webhooks write them as they are; a 1.1 caller gets each event encoded again with the 1.1 members. 1.0 and v0.3 callers never get a message update, and their responses never contain `generation`, `timeline` or the artifact placement. A 1.1 caller's own send stream starts after its message (the task it gets already holds it); other 1.1 streams of the task get the message update. A 1.1 send stream that reaches an interrupted state follows the task as a subscription until it is terminal; `MaxStreamDuration` still ends it. A task stored before this release gets its generation from its event log on its next change; its earlier history has no timeline entries.
- **A2A 1.1 generation features.** `ifGenerationMatch` is checked under the task lock on the record the commit is based on, after the duplicate check (a retry of an accepted message gets its outcome, not a mismatch). The long-poll waits for any event of the task (the generation equals the event sequence), at most `LongPollTimeout`, and answers at once for a terminal task; it holds a stream slot. `lastSeenGeneration` is a resume after that event sequence. A push config's `protocolVersion` defaults to the creating request's version; only `1.0` and `1.1` are accepted, and a 1.0 caller's config is always 1.0. A 1.1 webhook gets the stored event with `generation` added (before the webhook signature is computed), and the message updates; a 1.0 webhook gets exactly the 1.0 bytes. These 1.1 fields are ignored when a 1.0 caller sends them. Over HTTP+JSON the client sends the fields of GET calls in the query string (1.1 §11.5): `timelineLength` and `currentGeneration` on GetTask, `timelineLength` on ListTasks, and `lastSeenGeneration` on a GET subscribe. On streams, the client follows `generation` (1.1 §3.2.7): a gap is reconciled with GetTask (<xref:A2A.Client.A2AClientOptions.ReconcileGenerationGaps>, default true), events already reflected are dropped, generation is not used once the server sends 0 or repeats one on consecutive update events, and a reconnect without an event id resumes with `lastSeenGeneration`. See [Streaming](streaming.md#follow-a-task).
- **Client-written artifacts** (1.1 §3.2.1). One request names one task: an update without a message must carry the task id, and every update's task id, when set, must be the request's task. A request without a message runs no agent and answers with the task; on a stream it then follows the task like a subscription. It has no idempotency key of its own (there is no message id). An artifact id belongs to the side that wrote it. With a new task, the artifacts are stored when the task is created, so a direct reply stores neither message nor artifacts (§3.2.1). A signed card's `userArtifacts` is not covered by the signature (see Canonicalization), so a client of a signed card should not rely on it alone.
- **Live exchange** (1.1 §3.1.12). The spec does not say how an HTTP server tells the live stream from later input calls; we use the `Accept` header: `text/event-stream` opens the downlink, anything else is an uplink call that must name its task and answers with the task (no events, as the spec requires). A refused uplink call fails as a unary error and also sends a `StreamError` to the task's open downlinks of the same caller, so a client that reads only the stream sees it. A malformed request on a gRPC stream is refused on its own with its message id. Input reaches a running agent only when it reads `LiveInput`; otherwise the usual follow-up rules apply, so a message to a `WORKING` task is refused. See [Streaming](streaming.md#live-exchange-a2a-11).
- **Agent Card media type** (1.1 §14.1.2). The card endpoint answers `application/a2a-agent-card+json` only when the `Accept` header lists it, so a client that does not know the type gets `application/json` as before. The response has `Vary: Accept`.
- **gRPC interface address.** A card completed from the mapped bindings lists a gRPC interface over TLS as `host:port`, the form in the proto comment. A plain-text one keeps `http://host:port`, because clients read a bare `host:port` as TLS.
- **Telemetry.** See [Observability](observability.md). Spans and counters cost nothing while nobody listens.
- **Custom operations.** `AddExtensionOperation` adds a method of your own on every binding. The gRPC service `a2a.extensions.v1.A2AExtensionService` has the wire shape of the official A2A .NET SDK, which is not in the A2A spec, so it is `[Experimental]` (`A2AEXP004`). A call must activate the extension of the operation, or it fails with `ExtensionSupportRequired`. Operations are unary only. The built-in `lf.a2a.v1.A2AService` proto stays fixed. See [Custom operations](custom-operations.md) and <xref:A2A.Server.A2AServerBuilder.AddExtensionOperation*>.
